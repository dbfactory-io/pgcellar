# Decisions log

One line per decision, newest first. Date, decision, why.

- 2026-10-20 - A backup is followed by `barman switch-wal --force --archive` and never uses `--wait`. Why: on a quiet server the backup's end LSN sits in the WAL segment still being written; `barman backup --wait` then blocks until 16 MB of WAL or a switch (seen on the postiz test bed: 11 s of copy, 15 min of waiting). The forced switch closes that segment so the backup is restorable right away.
- 2026-10-20 - Container runs as the barman user (USER barman in the Dockerfile), not root. The CLI runner only prefixes `sudo -u barman` when the current user differs, and the image ships no sudo: found on the rasp001 test bed, where every `barman cron` tick failed with "sudo: executable file not found". Bind mounts (/etc/pgcellar, /etc/barman.d, the two volumes) must be owned by that uid; the systemd unit already ran as barman.
- 2026-10-20 - Audit noise: commands run for a user or an API key (backup, on-demand check, switch-wal, config writes) are always audited. Background commands (the `barman cron` ticker and the 60 s status refresh, actor "system") are audited only when the exit code is non-zero, and an identical failing command is logged at most once per hour. Why: one line per minute buried the audit log; the failures are what an admin needs. Audit lines older than audit_retention_days (default 90, 0 = keep forever) are purged daily.
- 2026-10-20 - Web/API milestone: one service layer (internal/app) behind both the HTML pages and /api/v1; handlers only translate. Why: what the UI can do the API can do, by construction.
- 2026-10-20 - Sessions: cookie holds a random token, the database holds only its SHA-256; the CSRF token is an HMAC of the session id with a secret kept in the settings table; login form uses a stateless HMAC token. Why: nothing replayable in SQLite, no extra column.
- 2026-10-20 - Config writes reload pgcellar.yaml from disk first, and the file is re-read when its mtime changes (if still valid). Why: files are the truth, a hand edit must not be overwritten.
- 2026-10-20 - Commits go to the repository of the pgcellar.yaml folder, plus a second repository in barman.config_dir when that folder is elsewhere. Why: /etc/barman.d is usually not under /etc/pgcellar.
- 2026-10-20 - Status colours: red = a check fails, no good backup, or last backup older than twice the limit; orange = any other problem (last attempt failed, backup older than alerts.max_backup_age, WAL older than max_wal_age); defaults 26 h backup and 24 h WAL when alerts are not set. Why: red must mean "act now".
- 2026-10-20 - Roles: viewer reads; operator also runs check, backup, switch-wal; admin also edits configuration and reads the audit log. Audit is admin-only because it holds exact command lines.
- 2026-10-20 - Barman cron interval is now barman.cron_interval in pgcellar.yaml (default 1m, 0 disables); --cron-interval on serve only overrides it. Why: config is now a typed struct, so Save no longer drops the key. Supersedes the earlier flag-only choice.
- 2026-10-20 - --dev works on a temporary copy of pgcellar.yaml and barman.d.example (git history is created there, deploy/ stays clean), freezes the clock at the fixtures time and resets admin/admin. Why: the example hash is a placeholder and the fixtures are static.
- 2026-10-20 - Name: pgCellar. The barman serves, the cellar keeps; pgcellar.io/.com/.app free at DNS level on that day.
- 2026-10-20 - Licence: FSL-1.1-Apache-2.0. Source available, free internal use, no competing hosted service, Apache-2.0 after two years. Chosen over BSL (four years) for the trust argument, over AGPL dual licensing (CLA, legal fear) and over MIT (nothing to sell).
- 2026-10-20 - Language: Go. Static binary, nobody compiles, contributions stay easy, and the GPL boundary with Barman is enforced by the stack (we can only run the command).
- 2026-10-20 - Barman is driven through its CLI and files only, never imported. GPL-3.0 boundary; the Docker image is a mere aggregation.
- 2026-10-20 - Configuration lives in text files (Barman's INI files + one pgcellar.yaml) with a local git history; SQLite only for run history, audit, sessions, api keys.
- 2026-10-20 - Front end: server-rendered templates + HTMX, no build step, no npm.
- 2026-10-20 - SQLite driver: modernc.org/sqlite (pure Go, no CGO) so cross-compilation stays trivial.
- 2026-10-20 - Pricing to test: Free 2 servers / Pro 490 EUR per year up to 10 servers / Business 1 490 EUR per year unlimited. Offline-verified Ed25519 licence keys.
- 2026-10-20 - Second engine (pgBackRest, MIT) designed for through the `Engine` interface, not built in 0.1.
- 2026-10-20 - Repository starts as private stranix79/pgcellar; it will be transferred to a dbfactory-io organisation (GitHub keeps redirects) and the module path updated before the first public release.
- 2026-10-20 - Barman 3.20.1 `--format json list-servers` returns an object indexed by server name (`{"chutag": {"description": "..."}, ...}`), identical with `--minimal`, not `{"_INFO": [...]}`; parser fixed, `--minimal` dropped, real captures kept in internal/barman/testdata/real.
- 2026-10-20 - Last archived WAL time comes from Barman's WAL catalogue file `<barman_home>/<server>/wals/<server>-xlog.db` (older versions: `xlog.db`), last line = last archived WAL (`name size epoch compression encryption`), read directly by Engine.Status (read-only, last 8 KiB); barman_home from barman.conf, default /var/lib/barman. Why not `barman diagnose`: it probes every server and takes 18-25 s on a Raspberry Pi, and Status runs once per server every minute; show-server, list-backups and replication-status carry no archive time. If the file cannot be read (pgcellar under another user than barman) the time stays unknown and the server shows a "Last WAL unknown" problem. ParseDiagnoseWAL stays for on-demand use.
- 2026-10-20 - `barman cron` runs once before the first status refresh (cronLoop runs it at startup, statusLoop waits for it): cron starts the receive-wal processes, and refreshing first made every server red for the first minute.
- 2026-10-20 - Each explain.go entry carries two sentences: `what` (what the check verifies, shown when it passes) and `bad` (what is wrong, shown and used in problems when it fails); the failing text used to repeat the passing one.
- 2026-10-20 - New `status_interval` key in pgcellar.yaml (Go duration, default 1m, minimum 30s, 0 or absent = default), wired to App.StatusInterval; the status footer shows the real interval. Why: one refresh starts 3 to 4 Python processes per server (2 to 4 s each on a Raspberry Pi 4), the testbed uses 5m.
- 2026-10-20 - Status reuses the previous `show-backup` result while the id of the last backup is unchanged (cache in CLIEngine, per server, in memory): a finished backup does not change, so this removes one of the four Barman processes per server per refresh.
- 2026-10-20 - On load, a config repository with no commit gets one "Import the existing configuration" commit (author pgcellar) holding what is on disk (`config.ImportExisting`, called from `app.Load` for the config dir and a separate barman.d); no-op when a commit exists. Why: hand-written configs left the History page empty and the first change showed up as the whole file.
- 2026-10-20 - Empty Runs page explains that only backups started from pgCellar are listed (string `runs.empty`); the API `/runs` keeps its shape (empty list). Why: barman-CLI and host-cron backups are invisible there and it looked like a bug.
- 2026-10-20 - API keys had no creation path (they are hashed entries in pgcellar.yaml): new `pgcellar apikey create|list`, same `NewAPIKey` and `Save` as the app, key printed once, change committed to the config history, running server reloads the file by itself. Why: the test bed cron needs a key and hand-hashing is error-prone.
- 2026-10-20 - Test bed cron calls `POST /api/v1/servers/<name>/backup` with `Authorization: Bearer <key>` (key in /etc/pgcellar-testbed.key, 600) instead of `docker exec barman backup`. Why: runs are recorded and audited, and StartBackup already chains switch-wal.
- 2026-10-20 - No page and no GET of the API runs Barman: `/servers`, `/servers/{name}`, `GET /api/v1/servers`, `/servers/{name}` and `/servers/{name}/backups` read the status cache and the barman.d files. Why: measured 2.9 s and 6.1 s per page on a Raspberry Pi (a Barman process costs 2 to 4 s), unusable with many servers. `Engine.Status` keeps the parsed `list-backups` in `ServerStatus.Backups`; a server missing from the cache gives "first refresh pending" (web) or 503 with Retry-After (API backups). "In Barman" on the list means "listed at the last refresh".
- 2026-10-20 - `POST .../check` ("Run check now") still calls Barman and now also updates that server's cache entry (checks, level, problems recomputed from the kept digest, no other command run). Backup and switch-wal stay explicit POST actions; a finished backup refreshes the server as before.
- 2026-10-20 - WAL semantics: on a quiet database a 16 MB WAL file fills rarely, so its age is not a health signal. State carries `streaming_live` (check receive_wal_running OK) and `last_data_received` (mtime of the newest file in `<barman_home>/<server>/streaming`, a file read, no command), next to the last filled WAL file (xlog.db). The WAL alert fires only when the receiver is not live, or when no data arrived for more than `alerts.max_wal_age`; servers with no receiver check (archive_command) keep the old rule on the last filled WAL file. A filled WAL file older than `max_wal_age` while streaming is live is only a note (advice: archive_timeout, for example 1h).
- 2026-10-20 - Vocabulary: "Last WAL" is replaced by "Last filled WAL file" and "Streaming: live / stopped" in the UI. JSON fields of the server state: `last_filled_wal`, `last_filled_wal_time`, `last_filled_wal_age_seconds`, `streaming_live`, `streaming_monitored`, `last_data_received`, `last_data_received_age_seconds`, `notes`, `stale`. The old `last_wal` and `last_wal_age_seconds` stay as deprecated aliases. Metrics: `pgcellar_last_wal_age_seconds` kept (last filled WAL file), added `pgcellar_last_wal_received_age_seconds` and `pgcellar_wal_streaming_live`.
- 2026-10-20 - The status cache is saved in SQLite (table `status_cache`: server, json, updated_at) after every refresh and reloaded in `app.Load`, flagged `stale` until the first refresh completes ("as of HH:MM, refreshing" in the footer and on the server page). Why: after a restart the pages are full at once instead of empty for up to a minute. The cache is rebuildable, so nothing depends on it.
- 2026-10-20 - Scaling stance: one pgCellar instance per Barman host, pages never run Barman, refresh costs about 3 Barman processes per server and interval; next steps (backup.info and xlog.db reads, separate longer `check_interval`, staggered servers, configurable parallelism, multi-host view) are written in docs/BRIEF.md "Scaling".
- 2026-10-20 - Visual direction of the web UI: warm and light by default (off-white `#FBF8F3`, near-black text `#1F1B18`, white cards with 14 px radius, thin borders, soft shadow), automatic dark palette through `prefers-color-scheme` (warm dark brown `#1C1917`, not a black dashboard), pill buttons with one primary per screen, system font stack at 17 px, no webfont, no JavaScript beyond HTMX. The public site is dark and cyan, so the product takes a warm cellar wine red as its single accent (`#8E1F3F` on light, `#F0839F` on dark; AA contrast checked) and keeps the wordmark `pgCellar`. Status opens with one human sentence and one large clickable line per server; emoji are signals always paired with a word and a coloured dot (✅ ⚠️ ❌ 🔄 💤 🍷 ✨); jokes only in empty states and successes, errors stay dry and say what to do.
- 2026-10-20 - Static assets are versioned by content: the layout links `/static/app.css?v=<first 12 hex of SHA-256>` (computed once at startup), served `immutable` for one year when `v` matches the current fingerprint and `no-cache` otherwise; HTML stays `no-store`. Why: after an update Safari kept the old `app.css` for an hour (max-age=3600) with new HTML, which broke the page.
- 2026-10-20: the mascot is an original elephant (wine glass held by the trunk), not Slonik: the PostgreSQL elephant is a trademark of the PostgreSQL Community Association, so we draw our own and keep clear of its shapes.
- 2026-10-20 - Deleting a complete backup is admin-only and runs `barman delete <server> <backup_id>` (text output, no JSON). pgCellar never second-guesses Barman: it refuses to go below `minimum_redundancy` and its message is returned as is (409 in the API, a red line in the page). The id must match `^[0-9]{8}T[0-9]{6}$` (422 otherwise) and the delete is audited as `backup.delete`. The command runs on a context detached from the HTTP request, so a closed browser tab cannot interrupt it half way.
- 2026-10-20 - Destructive actions in the web UI confirm inside the page, never with the browser's `confirm()`: HTMX swaps the row for a sentence and two buttons ("Delete" / "Keep it"). Why: native dialogs cannot be styled or tested, and are blocked in some embedded browsers.
- 2026-10-20 - Restore to a directory: `barman recover` runs locally (no `--remote-ssh-command`) into `<recoveries.dir>/<server>/<backup id>-<timestamp>`, as a run of kind `recover` (same mechanism as backups: recorded run, Barman output, exit code, duration, one restore per server at a time). New `recoveries:` section in pgcellar.yaml (`dir`, `max_download_bytes` 2 GiB, `keep_days` 7) and a `recoveries` table in SQLite. The folder is a volume mapped on the Docker host and owned by the barman uid, because the container runs as barman and a restore is as big as the database.
- 2026-10-20 - A restore path is always `<recoveries.dir>/<server>/<name>`, exactly two levels deep, with no symbolic link in the way; it is built from a validated server name and a backup id matching `^[0-9]{8}T[0-9]{6}$`, and checked again before every delete, purge and download. A database row pointing elsewhere is refused, never followed. Why: delete and purge run `RemoveAll`, so the path must not come from anything a user typed or a row can be tampered with.
- 2026-10-20 - Targets: `latest` (no target given to Barman), `backup_end` (`--target-immediate`: stop when the data is consistent) and `time` (`--target-time`, RFC 3339 or `YYYY-MM-DD HH:MM:SS+TZ`; a time without zone is read in the time zone of the server, which is what `datetime-local` means). `backup_end` uses `--target-immediate` rather than a target time equal to the end of the backup: a target time needs a WAL record dated after it, which a quiet database may never produce. The target time must not be before the end of the chosen backup (clear message); the upper bound is not checked, Barman reports missing WAL. Only a DONE backup can be restored.
- 2026-10-20 - The optional `.tar.gz` is built after the restore with `archive/tar` and `compress/gzip`, streamed (no file is loaded in memory), written as `.partial` and renamed when complete, next to the directory under the same name. If the restore succeeded but the archive failed, the directory is kept and recorded, and the run is marked failed with the reason. A failed `barman recover` removes its half-written directory. Download is `http.ServeFile` (byte ranges work) with `Content-Disposition: attachment`; 404 without archive, 413 above `max_download_bytes`.
- 2026-10-20 - Roles: operator starts a restore and downloads the archive, admin deletes one; viewers see the list and the paths but cannot download. Why: the archive is a full copy of the database, more sensitive than a backup list. Downloads are audited (`recovery.download`), as are `recover.start`, `recovery.delete` and `recovery.purge`.
- 2026-10-20 - Restores older than `recoveries.keep_days` are purged by the daily background pass, with the directory, the archive and the row; 0 keeps everything. `pgcellar_recoveries_total{server}` counts the successful `recover` runs per server (a counter read from the runs table, so a purge does not lower it).
- 2026-10-20 - Server setup: for each server pgCellar reads the PostgreSQL settings that Barman depends on with one read-only `psql` query on `pg_settings` (wal_level, max_wal_senders, max_replication_slots, archive_mode, archive_timeout, max_slot_wal_keep_size, full_page_writes, data_checksums, wal_compression, summarize_wal, server_version_num) and compares them with the client tools (`pg_basebackup --version`). The result is a list of lines (key, value, expected, level ok/info/warning/error, why, exact fix, restart or reload) shown in the "Server setup" section of the server page, on a pill in Status and Servers, in `GET /api/v1/servers/{name}/setup` and in the metric `pgcellar_setup_level{server}` (0 ok, 1 warning, 2 error). pgCellar never changes anything on the server: it only says what to change there.
- 2026-10-20 - psql goes through the audited runner: `CLIRunner.RunBinary(ctx, binary, args...)` is the same function as `Run` (same sudo rule, same audit entry, with `Binary` and `Target` added to the entry), and `Run` now calls it. CLAUDE.md says one function starts commands on a production database, so psql and pg_basebackup do not get a second code path. The password is never on the command line: a `password=` in conninfo is dropped before the call and psql reads the barman user's `~/.pgpass`; `connect_timeout=10` is added so an unreachable server cannot hold a refresh. Tests use `testdata/fake-psql` and `testdata/fake-pg_basebackup`, whose names are set in `App.SetupTools` (real names by default).
- 2026-10-20 - Cadence: the settings are read again only when the last result is older than `setup_interval` (pgcellar.yaml, default 30m, minimum 1m) or on "Run check now"; in between, the last lines are kept in the state (and in the SQLite status cache) and only the three lines derived from the cached `barman check` (streaming access, role privileges, replication slot) are recomputed, at no cost. A server whose settings could not be read is tried again after 5 minutes instead of 30. Why: settings change rarely, and one psql connection per server per minute is noise for the database and the audit log.
- 2026-10-20 - Warnings never change the health of a server, errors do: a setup warning (archive_timeout = 0, no max_slot_wal_keep_size, no data checksums) is advice, and counting it would turn the whole test bed orange; a setup error (wal_level minimal, max_wal_senders below 2, full_page_writes off, client tools older than the server, archive_mode off with archiver = on, failed streaming/privileges/slot checks) already makes Barman fail, so the server is Failing with a problem line. Exception: "Could not read the server settings" is a setup error for the pill but leaves the health alone, because Barman's own checks already say whether the server is reachable and a missing `~/.pgpass` for psql must not turn a working backup red. `max_slot_wal_keep_size = -1` is only a warning when `slot_name` is set (no slot, nothing holds WAL back, so it is shown as info).
- 2026-10-20 - Timeline: the "Timeline" section of the server page and `GET /api/v1/servers/{name}/timeline` are built on demand (a few milliseconds) from Barman's own files, read only: `<barman_home>/<server>/meta/<id>-backup.info` (fallback `base/<id>/backup.info` for older Barman), `wals/<server>-xlog.db` read in full (one line per archived WAL: name, size, epoch) and `wals/<timeline>.history`. No Barman command runs, so `TestPagesNeverRunBarman` still holds, and nothing is cached: the files are the truth and are small (one xlog.db line per 16 MiB of WAL). When `meta/` and `base/` are unreadable the model says `unavailable: <reason>` and the page shows that sentence.
- 2026-10-20 - Earliest point in time: the `end_time` of the oldest backup with status DONE whose WAL chain is unbroken, segment by segment, from its `begin_wal` to the newest archived WAL file (the head, by archive time). The walk follows a fork: when the next segment is missing on the current timeline, it continues on a child timeline that leads to the head's timeline if its `.history` fork point is that segment. Without a history file the fork is unknown and the chain is broken. If the oldest backup fails the test the next one is tried; none qualifying means no restore range. Latest point: the last byte received when streaming is live (`last_data_received`), else the arrival time of the last filled WAL file. Why end_time and not begin_time: Barman refuses a target time before the end of the chosen backup, so announcing the start would be wrong by the duration of the backup (changed from begin_time the same day). The backup block in the picture still spans begin to end.
- 2026-10-20 - Timeline picture: one inline SVG written by the server (`html/template`, viewBox 640 wide, no script, no library, colours from CSS classes so light and dark follow the page, a `<title>` on every element). The axis starts a little before the oldest backup or WAL file (at least two hours wide) rather than 7 days back: with a few hours of history a 7 day axis squeezes everything into the right edge. The retention window is drawn clipped to the axis and its length is in the sentence under the picture. The axis is stretched to the next planned backup only when it is within a third of the span. WAL "between two backups" means files archived after the begin of one DONE backup up to the begin of the next; sizes are the bytes in xlog.db (as stored, compressed). A hole in the WAL is a missing segment number between two files of the same timeline and is drawn on the span between the arrival of the segment before and after it. Labels are placed greedily on two rows and dropped when they would overlap; below about 450 px the picture scrolls sideways inside its card and the sentence under it carries the same facts.
- 2026-10-20 - SSH key: one ed25519 pair per pgCellar, generated on first use of the "SSH key" page (admin only) or of the connection test, in `~/.ssh` of the Barman user (`id_ed25519` 0600, `id_ed25519.pub` 0644, directory 0700), never replaced if present (a missing `.pub` is rebuilt from the private key). Why: Barman's `rsync` method and `ssh_command` already use the default key of that user, so there is nothing to configure. Only `internal/sshkeys` touches the private key; no function returns it, and the page, the API and the audit log carry the public line (`ssh-ed25519 ... pgcellar@<hostname>`) only. Creation is audited as `sshkey.create`.
- 2026-10-20 - The connection test runs `ssh -o BatchMode=yes -o ConnectTimeout=10 <rest of ssh_command> true` through the audited runner (`RunBinary`). The options go right after `ssh` and not at the end, so they can never be read as the remote command. The command is split on spaces (no shell, no quoting) and must start with `ssh`; anything else is refused without running. The result shows ssh's own error text unchanged. BatchMode means a host key unknown to `known_hosts` fails: the page tells to connect once by hand.
- 2026-10-20 - WAL method is a form choice over two Barman switches: `streaming` = `streaming_archiver = on` + `archiver = off` (default for postgres), `archive_command` = `archiver = on` + `streaming_archiver = off` (default for rsync), `both` = both on, the resilient setup Barman allows. It is not stored in pgcellar.yaml: it is derived from the two keys when the file is read, and an input without `wal_method` leaves the file as it is (older API clients). `backup_method = postgres` + `archiver = on` is valid (pg_basebackup for the base backup, `archive_command` for WAL, no slot needed; `streaming_conninfo` stays required for pg_basebackup). `rsync` still needs `archiver = on` and `ssh_command`, so WAL method `streaming` is refused for rsync; `rsync` with streaming also needs `streaming_conninfo`. `create_slot = auto` is only added when streaming is on.
- 2026-10-20 - Server setup with `archiver = on`: `archive_mode` is an error when off (restart), and `archive_command` is read from `pg_settings` and is an error when empty or when it neither contains `barman-wal-archive` nor writes into `incoming/` (the rsync alternative); otherwise info, with the exact `ALTER SYSTEM SET archive_command = 'barman-wal-archive <ssh_host> <server> %p'; SELECT pg_reload_conf();`. pgCellar cannot test the command from its side; the proof is `switch-wal --archive` then `barman check`. A role that cannot read the value (`<insufficient privilege>`) gets an info line telling to grant `pg_read_all_settings`. Barman's own verdicts `wal_archive`, `archive_command` and `archive_mode` from the cached `barman check` are added as derived lines. `ssh_host` (pgcellar.yaml) is the host name shown in the advised command; default is the machine's host name, which in Docker is the container id, so set it there.
- 2026-10-20 - Not decided, to settle with the owner: WAL shipping needs an SSH server on the pgCellar side (PostgreSQL connects to `barman@host`). The Docker image has only `openssh-client`. Options: sshd on the Docker host sharing the volume, an SSH sidecar container, or `sshd` in the image run by an entrypoint (a second process, and root or a high port).
